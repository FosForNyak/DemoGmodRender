# Підпроєкт 1: оболонка Anvil + імпорт .dem — дизайн

**Дата:** 2026-09-30 · **Слаг:** `app-shell-demo-import` · **Статус:** затверджено (користувач дав постійний дозвіл не питати затвердження розділів)

Перший підпроєкт дає настільний застосунок на дизайн-системі Anvil, який відкриває справжні демо GMod без запуску гри: розбирає .dem у базу стану, показує сутності, їхні властивості в будь-який тік, події на таймлайні, камеру автора, вигляд карти зверху й звіт про контент, якого бракує. Рендер 3D-сцени — наступний підпроєкт; в'юпорт тут — вигляд зверху й заглушка.

Джерела: «Рушій рендеру демок Garry's Mod: архітектура» (вкладки Архітектура, Слабкі місця, NW / NW2, Оптимізація), дизайн-система Anvil, спайк на двох реальних демо (розділ 4).

## 1. Межі

**Входить:**

1. Застосунок Tauri 2 для Windows: вікно без рамки, TitleBar Anvil, Workspace, панелі, таймлайн, налаштування, палітра команд.
2. C++20-ядро: `core`, `demo`, `assets`, `api` + `gmdr-import` (дочірній процес) + `gmdr-cli`.
3. Повний розбір .dem протоколу 24 у варіанті GMod: заголовок, команди, повідомлення, string tables, SendTables і класи, PacketEntities з PVS і baseline, події, камера автора.
4. База стану `state.gmstate` з ключовими знімками й поступовою доступністю під час імпорту.
5. Пошук GMod і контенту: Steam, `mount.cfg`, VPK, GMA (Workshop і кеш сервера), `download/`, pakfile карти; звіт «чого бракує».
6. CI: Windows (MSVC, ядро + застосунок) і Linux (GCC, Clang, ASan/UBSan) для ядра й тестів.

**Не входить (наступні підпроєкти):** RHI і 3D-рендер, BSP-геометрія, MDL, анімація, звук, вивід у відео, шари редагувань, проєкт у SQLite, GLua, супутник запису, Linux-застосунок (WebKitGTK), AppContainer-подібна пісочниця на Linux, декодування вмісту NW/NW2 і net-повідомлень (зберігаються сирими з назвою).

## 3. Архітектура

```
┌──────────────── DemoGmodRender.exe (один процес) ─────────────────┐
│  WebView2 · React 18 + Anvil (window.Anvil, IBM Plex, tokens.css)  │
│        │ invoke("engine_call", {cmd, args}) · подія "engine"        │
│  Rust · Tauri 2: вікно, діалоги, drag&drop, кнопки вікна            │
│        │ C ABI: gmdr_create/gmdr_call/gmdr_free/gmdr_set_event_sink │
│  C++20 ядро (static lib): core → demo → assets → api                │
│        │ читає лише state.gmstate: кожен зсув і розмір перевіряються │
└────────┼───────────────────────────────────────────────────────────┘
         │ запуск з двома успадкованими дескрипторами
┌────────▼──────── gmdr-import.exe (дочірній процес) ────────────────┐
│  модуль demo · Job Object: ліміт пам'яті 4 ГБ, 1 процес,            │
│  kill-on-close · stdout: JSON-рядки прогресу й готових чанків        │
└─────────────────────────────────────────────────────────────────────┘
gmdr-cli.exe: headless-клієнт тих самих команд (info · import · query)
```

- **Залежності модулів лише згори вниз:** `core` ← `demo` ← `assets` ← `api`. `scene`, `sim`, `render`, `output` не створюються.
- **Командна шина.** Кожна можливість — іменована команда з JSON-аргументами й JSON-результатом. UI, CLI й майбутній скриптовий API — клієнти однієї таблиці. Rust лише пересилає.
- **Потоки.** `gmdr_call` потокобезпечний; кожне відкрите демо має свій м'ютекс і власний потік, що читає stdout імпортера. Події (прогрес, готові чанки, журнал) йдуть через callback у Rust → подія Tauri `engine`.
- **Типи, що не змінюються потім:** `EntityUid` u64 = BLAKE3-64 від (хеш демо, індекс, serial, тік появи); `Tick` i64; `Flicks` i64 (1/705 600 000 с) для часу таймлайну; лише x64.

## 4. Формат .dem у варіанті GMod — підтверджено спайком

Спайк (Python, поза репозиторієм) пройшов обидва локальні демо: `25_07_2025.dem` (109 МБ, 148 959 тіків, 33 тік/с) і `29_08_2026.dem` (183 МБ, 216 672 тіки, 66 тік/с). Друге розбирається на рівні повідомлень без жодної помилки (215 740 пакетів), перше — з однією помилкою в сигнон-пакеті 3.

| Що | Факт | Наслідок для парсера |
| --- | --- | --- |
| Заголовок | 1072 байти, `GMODEMO`, demo protocol 3, network protocol 24 | приймати й `HL2DEMO` |
| Команди | 1 signon, 2 packet, 3 synctick, 4 consolecmd, 5 usercmd, 6 datatables, 7 stop, 8 stringtables; байта player slot немає | обхід довжинами дає швидкий індекс: 0,4 с на 109 МБ навіть у Python |
| Пакет | `democmdinfo` 76 байт + seq in/out + i32 довжина + дані | камера автора з кожного пакета |
| Тип повідомлення | 6 біт | — |
| `svc_ServerInfo` | стандартні поля SDK 2013 + рядок `sv_loadingurl` + рядок gamemode + 16 біт (`0xFFFF` в обох демо) | варіант `gmod-2025` |
| `svc_CreateStringTable` | ім'я; **4 біти log2(maxEntries)**; numEntries (log2+1 біт); **1 невідомий біт**; довжина **varint32**; fixed userdata (1 + 12 + 4); compressed (1); дані | відрізняється від SDK 2013 — варіант GMod |
| `svc_UpdateStringTable` | id 5 біт, опційно u16 кількість, довжина 20 біт | як SDK 2013 |
| `svc_PacketEntities` | maxEntries 13 біт, delta (1 + i32), baseline 1, updated 13 біт, довжина **24 біти**, updateBaseline 1 | EDICT_BITS 13, DELTASIZE_BITS 24 |
| `svc_GMod_ServerToClient` | id 33, довжина 20 біт | зберігати сирим з назвою з таблиці `networkstring` |
| `svc_UserMessage`, `svc_EntityMessage`, `svc_GameEvent` | довжина 11 біт | як SDK 2013 |
| `svc_TempEntities` | кількість 8 біт, довжина varint32 | — |
| String tables | 19 таблиць, зокрема GMod-специфічні `networkstring` (346 назв net-повідомлень), `networkvars` (ключі NW), `client_lua_files` (1290 файлів), `GameRulesCreation` | маніфест контенту й назви net-повідомлень без гри |
| Невідоме | сигнон-пакет 3 першого демо — повідомлення типу 2 з нестандартною будовою, 400 байт, до появи сутностей | пакет, що не розібрався, записується як подія «не розібрано» (тік, зсув, причина); імпорт іде далі з наступного пакета |
| Хвости пакетів | після останнього повідомлення — NOP-вирівнювання й сміттєві біти в останньому байті | не помилка |

**Ще не підтверджено (перевірка — перше завдання реалізації на C++):** ширина прапорців SendProp (16 біт, як SDK 2013), набір типів властивостей (чи є Int64), порядок «сплющування» з SPROP_CHANGES_OFTEN (однопрохідний swap SDK 2013), кодування індексів властивостей (`while ReadOneBit(): idx += 1 + ReadUBitVar()`). Критерій правильності — розділ 13.

### 4.1 Варіанти протоколу

Усе, що відрізняється між збірками, зібрано в структуру `ProtocolVariant` (ширини полів, будова ServerInfo і CreateStringTable, id повідомлень GMod). Автовизначення: сигнон-пакети пробуються з кожним відомим варіантом; перемагає той, з яким усі повідомлення сигнону розбираються до кінця пакета. Новий варіант = новий запис у таблиці + демо в корпусі.

### 4.2 Що декодується в цьому підпроєкті

| Повідомлення | Що зберігаємо |
| --- | --- |
| ServerInfo, SetConVar, SignonState, Print | інформація про демо: сервер, мапа, gamemode, tick interval, maxclients, loading URL, конвари |
| Create/UpdateStringTable, dem_stringtables | стан таблиць у кожен тік (історія змін), з обробкою compressed (LZSS Valve) |
| dem_datatables, ClassInfo | схема: SendTables, класи, сплющені властивості |
| PacketEntities | життя сутностей, PVS, усі властивості |
| GameEventList, GameEvent | події з іменами й полями |
| TempEntities | тік, кількість, клас першого запису; сирі біти |
| Sounds, VoiceData, UserMessage, EntityMessage, GMod net (33), BSPDecal, SetView, FixAngle, CrosshairAngle, Menu, Prefetch | тік, тип, розмір, короткий підсумок (для 33 — назва з `networkstring`, для BSPDecal — позиція й індекс декалі) і посилання на біти в .dem (зсув пакета, біт, довжина) |
| democmdinfo | камера автора: позиція, кути, локальні кути для кожного пакета |
| consolecmd | тік і текст команди |

Сирі дані не копіюються: подія зберігає зсув у .dem, бо демо — єдине джерело правди. Голос інших гравців не декодується.

### 4.3 Ліміти (Слабкі місця, S7)

Перед кожною алокацією: розміри string tables ≤ 65 536 записів, рядок ≤ 4096 байт, SendTables ≤ 4096 таблиць і ≤ 1024 властивостей у таблиці, глибина вкладення ≤ 32 з детектором циклів, класи ≤ 8192, масив ≤ 1024 елементи, довжина повідомлення ≤ залишку пакета, пакет ≤ 16 МБ, decompressed LZSS ≤ 64 МБ. Порушення → чиста помилка з кодом, без аварії.

## 5. Імпорт

1. **Відкриття.** Головний процес рахує BLAKE3 .dem (потоково) → ключ кешу `%LOCALAPPDATA%\DemoGmodRender\cache\demos\<hash>\`. Якщо там уже є повний `state.gmstate` тієї ж версії формату — відкривається одразу.
2. **Запуск імпортера.** Головний процес відкриває .dem на читання і `state.gmstate.part` на запис, запускає `gmdr-import --in-handle N --out-handle M` з успадкованими дескрипторами в Job Object. Імпортер не відкриває жодного шляху.
3. **Прохід 1 — швидкий індекс** (секунди): зсуви всіх команд, тіки, кількість пакетів → чанк `INDEX` + подія `import.indexed {ticks_total}`. Таймлайн має повну довжину одразу.
4. **Прохід 2 — повне декодування** послідовно: кожні 30 с демо-часу — чанк `KEYFRAME`, між ними — `DELTAS`, `EVENTS`, `CAMERA`, `STRINGTABLES`. Після кожного чанка — рядок `{"chunk":{...}}` у stdout; головний процес одразу може його читати. Подія `import.progress {tick_ready, ticks_total}`.
5. **Кінець:** чанки `LIVES`, `MANIFEST`, `DIRECTORY`, потім заголовок з прапорцем «повний»; головний процес перейменовує `.part` → `state.gmstate`.
6. **Скасування й збій:** закриття демо чи застосунку вбиває Job Object; `.part` видаляється при наступному відкритті. Помилка імпортера → останній рядок `{"error":{code,message,tick}}`, готова частина лишається доступною з позначкою.

Ціль: 183-МБ демо імпортується повністю ≤ 15 с на цьому ПК; перші дані на таймлайні ≤ 1 с.

## 6. База стану `state.gmstate`

**Файл:** заголовок 64 байти (`GMSTATE\0`, версія формату, прапорці, BLAKE3 демо, версія парсера), далі чанки, що лише дописуються, в кінці — `DIRECTORY`. Чанк: заголовок (вид u16, прапорці, `tick_from`, `tick_to` i64, сирий і стиснутий розмір u32, контрольна сума XXH3-64) + корисне навантаження zstd (рівень 3).

| Чанк | Вміст |
| --- | --- |
| `INDEX` | тік → зсув команди в .dem |
| `SCHEMA` | класи, сплющені властивості (ім'я, тип, прапорці, біти, межі), таблиці рядків (імена) |
| `KEYFRAME` | повний стан усіх сутностей у PVS на тік: для кожного класу — стовпці властивостей по сутностях |
| `DELTAS` | зміни в (keyframe_k, keyframe_k+1]: по класах і властивостях — масиви (Δтік varint, слот сутності varint, значення); вхід/вихід PVS, видалення |
| `EVENTS` | (тік, вид, підсумок, посилання на біти в .dem) |
| `CAMERA` | тік, позиція, кути, локальні кути |
| `STRINGTABLES` | зміни таблиць рядків (тік, таблиця, індекс, рядок, userdata) |
| `LIVES` | життя: uid, індекс, serial, клас, тік появи/зникнення, інтервали в PVS |
| `MANIFEST` | потрібний контент: мапа, моделі, звуки, декалі, downloadables (зокрема ID Workshop), клієнтський Lua (лише список) |
| `DIRECTORY` | список чанків зі зсувами (для швидкого відкриття повного файлу) |

**Значення за типами:** int → zigzag varint; float → f32; vector → 3 × f32; string → індекс у пул рядків чанка; array → довжина + елементи. Поза PVS значення «невідоме», а не нуль.

**Читання** (головний процес): позиційні читання чанків, перевірка контрольної суми й меж, розпакування, LRU декодованих чанків (ліміт 512 МБ). `state_at(tick)` = найближчий `KEYFRAME` ≤ tick + застосування `DELTAS` до tick; для послідовного програвання — інкрементний крок вперед від останнього стану. Цілі: довільний перехід ≤ 100 мс, крок кадру ≤ 16 мс, розмір файлу ≤ 0,4 × .dem.

**Версії:** номер формату в заголовку; інша версія → перебудова (кеш, не дані користувача).

## 7. Контент GMod

1. **Пошук Steam і GMod:** реєстр `HKCU\Software\Valve\Steam\SteamPath` → `steamapps/libraryfolders.vdf` → бібліотека з appid 4000 → `steamapps/common/GarrysMod`. Ручний шлях у налаштуваннях перекриває. Жодного запису в теку гри (S13).
2. **VFS** у порядку пошуку GMod: `garrysmod/` (теки) → `garrysmod/addons/*/` → GMA з `garrysmod/cache/workshop/*.gma` і `steamapps/workshop/content/4000/*/*.gma` → `garrysmod/garrysmod_dir.vpk`, `garrysmod/fallbacks_dir.vpk` → `sourceengine/*_dir.vpk`, `platform/platform_misc_dir.vpk` → ігри з `cfg/mount.cfg` (теки й `*_dir.vpk`) → `garrysmod/download/` → pakfile карти (lump 40 BSP, ZIP). Шляхи без регістру, `\` → `/`. Файли `.cache` і `_legacy.bin` (старі LZMA-кеші Workshop) — лише рахуються як «Workshop, не розпаковано».
3. **Перевірка:** для кожного ресурсу з `MANIFEST` — знайдено (де: тека, VPK, GMA з ID, pakfile) / бракує. ID Workshop з `downloadables` (`3001397905.gma`) → «встановлено / немає в кеші».
4. Парсери VPK, GMA, ZIP, VDF — у головному процесі лише для **локальних** файлів інсталяції, з тими самими читачами з перевіркою меж і фазингом; сам BSP-pakfile розбирається в імпортері (дані з демо вказують на мапу, яку може підкласти сервер).

- **Вікно:** `decorations: false`, мінімум 1024 × 640, TitleBar `platform="windows"`, `data-tauri-drag-region`, подвійний клік розгортає; стан вікна й макет DockLayout зберігаються в налаштуваннях.

## 11. Безпека

- **Межа довіри:** .dem і все, що з нього, — чужі дані. Розбір лише в `gmdr-import`: успадковані дескриптори, Job Object (пам'ять 4 ГБ, без дочірніх процесів, kill-on-close, таймаут простою 60 с без прогресу), AppContainer — останнє завдання підпроєкту.
- **Читачі** лише через `ByteReader`/`BitReader` з перевіркою меж і арифметикою без переповнень; жодних `reinterpret_cast` структур поверх байтів файлу.
- **Головний процес** не довіряє `state.gmstate`: контрольні суми, межі, версія.
- **Tauri:** CSP `default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'`, жодних віддалених URL, мінімальні capabilities (свої команди, кнопки вікна, діалог відкриття файлу), без shell-плагіна. Шляхи — лише з діалогу чи drag&drop.
- **Приватність (S12):** імена й SteamID інших гравців лише локально; журнал без персональних даних за замовчуванням; телеметрії немає. Реальні демо не потрапляють у репозиторій.
- **Фазинг:** libFuzzer + ASan/UBSan для заголовка й команд, повідомлень, string tables, SendTables, PacketEntities, LZSS, VPK, GMA, ZIP, VDF, читача `state.gmstate`.

## 12. Тестування й CI

1. **Юніт (doctest):** BitReader (межі, UBitVar, varint, coord/normal/coordMP), декодери властивостей, сплющування SendTables на синтетичних таблицях, string tables (зокрема compressed), LZSS, VPK/GMA/ZIP/VDF, statedb (запис → читання → однаковий стан), ліміти.
2. **Корпус (локально, змінна `GMDR_CORPUS`):** обидва демо розбираються; знімок-підсумок (кількість тіків, пакетів, подій за видами, класи, кількість життів, хеш стану в 10 тіках) порівнюється з еталоном у `tests/corpus/*.summary.json` без самих демо.
3. **Rust:** `cargo test` для обгортки FFI; **UI:** `vitest` для логіки стану й форматування.
4. **Застосунок:** запуск, відкриття демо, скріншоти ключових станів (перевіряє QA).
5. **CI (GitHub Actions):** Windows — CMake preset `windows-msvc`, ctest, `npm ci && npm run build && cargo build`; Linux — `linux-gcc`, `linux-clang-asan`, ctest, фазинг по 60 с на ціль. Спершу збирається ядро й тести; пакування інсталятора — окремий job без публікації.
